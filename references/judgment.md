## 1. 판정 정의와 증거

| 판정 | 조건 | 필수 필드(verdict.py 가 검사) |
|---|---|---|
| P | 기대 결과를 **전부** 관찰함 | `--evidence`(스크린샷 경로 · API 응답 요지 · DB 조회 결과) |
| F | 기대와 다름 | `--sev` · `--actual` · `--evidence` · `--repro` |
| NA | 범위 밖으로 **문서상 확정** | `--actual`(근거 문서) |
| BLOCKED | 이 환경에서 판정 불가 | `--actual`(사유 · 시도한 것) |

- **P 에도 증거가 필요하다.** 증거 없는 P 는 "안 해 봤다"와 구별되지 않는다. 회차가 거듭되면 "그때 정말 됐나"를 다시 물을 수 없다.
- 증거는 다시 열어 볼 수 있어야 한다. 스크린샷 경로, 응답의 상태코드와 오류 code, DB 조회 결과 한 줄을 남긴다. "확인함"은 증거가 아니다.
- 비밀 값은 증거에도 쓰지 않는다. `verdict.py` 가 프로필 `redact_patterns` 에 걸리는 값이 든 기록을 거부한다.
- NA 는 남용되기 쉽다. "구현이 덜 됐다"는 NA 가 아니다. 명세가 요구하면 F 다. NA 는 범위 밖이 문서(결정 로그·범위 문서)로 확정된 것에만 쓴다.
- **승인 대기**(`changes.md` §2)에 걸린 동작은 그 항목이 기대문을 **임시로 대신한다.** 지금 동작이 §2 에 적힌 "지금 동작"과 같으면 P + note `승인 대기 <항목>` 이다. 다르면 F 다. 그 TC 의 나머지 기대 결과는 원래대로 전부 관찰해야 P 다. 승인 대기 P 는 GO 판정에서 P 로 세고, 보고서의 "승인 대기" 목록에 따로 올린다.

## 2. 오판을 막는 규칙 — 전부 실제 오판에서 나왔다

- **"없다" F 는 의심부터 한다.** 화면에 없다고 F 를 주기 전에 확인한다. 끝까지 스크롤했는가, 다른 탭·접힌 영역·하단 시트를 열어 봤는가, dump 와 스크린샷을 둘 다 봤는가. 어떤 회차에서는 "없다" F 5건이 전부 오판이었다(스크롤 아래·다른 탭에 있었다).
- **기대문을 의심할 줄 안다.** 명세끼리 충돌하거나 근거 문서에 없는 기대문이면 F 를 주지 않는다. BLOCKED + note `기대문 의심 — <이유>` 로 둔다. 메인이 근거 문서를 다시 열어 TC 를 정정하거나 사람에게 묻는다. 틀린 기대문으로 F 를 쌓으면 수정 루프가 멀쩡한 코드를 고치게 된다.
- **문구 차이**: 띄어쓰기·문장부호처럼 의미가 같은 차이는 P + note 다. 의미가 바뀌면 F(Minor 부터)다. 금액·날짜·상태명처럼 사용자가 행동을 정하는 문구가 틀리면 Major 이상이다.
- **시각 판정은 스크린샷을 열어서 한다.** 위젯·DOM 트리에 요소가 있다고 해서 사람 눈에 보이는 것은 아니다. 흰 배경에 흰 글씨, 화면 밖으로 밀린 버튼, 다른 요소에 가려진 입력칸이 전부 트리에는 있었다. 볼 것은 대비, 잘림, 겹침, 화면 밖, 로딩 종료, 같은 역할 화면끼리의 일관성이다.
- **"됐다"는 끝까지 간 뒤에 말한다.** 제출 버튼을 눌렀다는 것과 서버에 기록됐다는 것은 다르다. 핵심 여정 TC 는 서버 응답·DB 행·목록 반영까지 확인한다.
- **지난 F 는 같은 재현 절차로 다시 밟는다.** 다른 길로 가서 P 를 주면 결함이 고쳐졌는지 알 수 없다. 고쳐졌으면 `--fix 해소`, 일부 갈래만 고쳐졌으면 F + `--fix 부분` 을 쓰고 남은 갈래를 note 에 적는다.
- **간헐 결함은 횟수를 적는다.** "5회 중 4회"처럼 쓴다. 1회 재현은 부수 기록으로 남기고 재확인 레인이 다시 밟는다.
- **환경 갭을 제품 결함으로 적지 않는다.** 스키마 마이그레이션 누락, 마스터 코드값의 환경 차이, 테스트 계정 권한 부족이 여기에 해당한다. 서버 로그·DB 를 보고 "이 커밋이 기대하는 환경인가"를 먼저 확인한다. 환경 갭이면 BLOCKED + note `환경 갭 — <무엇>` 으로 두고 메인이 환경을 고친다.
- **레인이 고치지 않는다.** 데이터를 손으로 맞춰서 P 를 만들지 않는다. 데이터 준비는 TC 의 `data_setup` 과 상태 시드 도구 범위 안에서만 한다.

## 3. 심각도

| 등급 | 기준 |
|---|---|
| **Critical** | 강제 종료·먹통 · **핵심 여정을 끝까지 못 감**(우회 경로가 "처음부터 다시"뿐인 경우 포함) · 데이터가 틀리게 저장·표시(남의 데이터·틀린 상태·금액·일정) · 보안(인증 우회·타인 정보 노출·비밀 노출) · 중복 생성·되돌릴 수 없는 오동작 |
| **Major** | 명세된 기능이 안 되거나 결과가 틀림(핵심 여정 밖) · 오류 처리 누락으로 막히거나 오해(무한 로딩·빈 화면·엉뚱한 안내) · 필수 정보/버튼 누락·읽을 수 없음(겹침·잘림·대비) · 뒤로가기/이동이 엉뚱한 곳 · 완료 화면이 안 뜸 · 같은 역할 화면끼리 구조가 크게 다름 |
| **Minor** | 문구·오탈자·띄어쓰기 · 정렬·여백·아이콘·색 등 경미한 시각 차이 · 사소한 불편(개선 제안 수준) |

다시 매길 때 보는 것:
- **레인은 낮게 적는 경향이 있다.** "안내대로 해도 못 고치고, 처음부터 다시 쓰는 것 말고는 길이 없다"면 레인이 Major 라고 적었어도 Critical 이다.
- **노출 범위**를 본다. 같은 증상이라도 기본 경로(모든 사용자)에 있으면 한 단계 올리고, 드문 조합에서만 나면 그대로 둔다.
- **간헐**이어도 핵심 여정이면 등급을 낮추지 않는다. 사용자는 횟수를 고르지 못한다.
- **디자인 일관성**은 같은 역할 화면끼리 구조가 다르면 Major, 세부 수치 차이는 Minor 다. 개선(improve)은 결함이 아니다. 명세와 다르지 않은 더 나은 안은 제안 목록으로 따로 남긴다.

## 4. 감사 순서 — 메인이 직접 한다

```bash
python $S/triage.py --json RUN/triage.json
```

출력 순서대로 처리한다.

1. **결함별 상태**: 지난 결함마다 이번 회차 기록을 대조한다. `fixed 후보`(관련 TC 가 P), `재발(F)`, `미확인 — 재확인 레인 필요`(TC 밖 부수 결함), `미확인(이번 회차 기록 없음)`, `판정 보류` 로 가른다. `fixed 후보` 는 P 의 evidence 를 읽고 **예전 재현 절차를 밟은 증거인지** 확인한 뒤에 `defects.py set <ID> --status fixed` 한다.
2. **새 F**: 각 F 의 actual·evidence·repro 를 읽는다. 스크린샷은 직접 연다. "없다"류, 문구 차이, 기대문이 의심스러운 F 는 근거 문서(`source`)를 다시 연다. 셋 중 하나로 결론 낸다: 확정 / 오판(재측정 레인으로) / 기대문 정정(사람 결정 필요하면 `changes.md` §2).
3. **부수 결함**: §6.
4. **BLOCKED**: §5.
5. **등급1 잔여**: 등급1 중 P·NA 가 아닌 것을 본다. 하나라도 남으면 NO-GO 다.
6. **레인의 "해소" 주장**: `--fix 해소` 를 단 기록을 대조한다. 같은 TC 의 다른 갈래가 F 면 "부분"이다.
7. 결론을 `defects.py add|set` 으로 반영하고, 숫자는 `render_results.py --stats` 로 다시 뽑는다. 손으로 세지 않는다.

레인 보고를 그대로 믿지 않는다. 레인 여럿이 "다 됐다"고 보고했는데 실제로는 배정 TC 의 일부만 기록돼 있던 일이 있다. 반환이 비어 있거나(에이전트 사망) 응답이 없는 레인도 나온다. 판정 수는 jsonl 에서 센다. 결과가 없는 레인은 **결과가 없다는 사실을 보고서에 적고** 그 묶음만 새 run 으로 다시 돌린다.

## 5. BLOCKED 가르기

| 사유 | 처리 |
|---|---|
| 환경 한계(실기기·외부 실계정·푸시·iOS) | 그대로 둔다. 보고서의 "이 환경에서 못 잰 것" 목록에 올린다 |
| 다른 레인 뒤에 해야 함(`[순서 필요: …]`) | 모아서 `recheck.js` 의 ordered 로 한 번에 돈다(빈 계정·탈퇴 뒤 등) |
| 데이터를 못 만듦 | 상태 시드 도구로 만들 수 있으면 도구를 고쳐(메인) 재측정한다. 앱 기능으로만 만들 수 있는데 그 기능이 고장이면 그 결함에 TC 를 묶는다 |
| 레인이 길을 못 찾음 | `notes-<lane>.md` 에 길을 적고 재측정 레인으로 보낸다 |
| 기대문 의심 | 근거 문서를 다시 연다 → TC 정정 또는 사람 결정 대기(`changes.md` §2) |
| 환경 갭 | 메인이 환경을 고친 뒤 재측정한다. 고칠 수 없으면 보고서에 적는다 |
| 서버 다운 | 원인 확인(메모리 부족으로 프로세스가 정리됐는지 등) → 서버를 오래 사는 pane 으로 옮기고 재측정 |

## 6. 부수 결함과 재확인

TC 밖에서 본 결함은 놓치기 쉽지만 실제로 Major 가 많이 나온 곳이다. 핵심 여정 TC 를 하다가 옆 화면에서 본 것들이 여기에 해당한다.

1. 레인은 `verdict.py --side --sev <등급> --title "…" --actual "…" --repro "…"` 로 남긴다. 어느 TC 를 하다가 봤는지 note 에 적는다.
2. 메인은 비슷한 기록(같은 화면·같은 증상)을 하나로 묶는다. 두 레인 이상이 독립적으로 봤다면 그것만으로 확정 근거가 된다.
3. 1회만 관측된 것은 `lanes/recheck.md` 에 적는다(템플릿 `assets/templates/recheck.md`). 시작 상태·재현 절차·예전 현상·고쳐진 동작·갈래·정리 순서다.
4. `recheck.js` 로 재확인 레인을 돌린다. 결과는 `fixed / still / blocked` 다. 재확인 레인은 verdict.py 로 쓰지 않고 구조화 출력으로 돌려준다. 결함 상태는 메인이 정한다.
5. still 이면 확정하고, blocked 면 사유를 보고 다음 회차로 넘긴다. 다음 회차 재확인 목록에 남긴다.

## 7. 병합 — 가장 나중 기록이 이긴다

- 판정 원본은 `out/*.jsonl` 이다. 같은 TC 의 기록이 여럿이면 **시각이 가장 늦은 기록**이 그 TC 의 판정이다. 재측정 레인이 앞 기록을 지우지 않고 덧붙이면 된다.
- 지난 회차 파일은 `out/r<N>-<lane>.jsonl` 로 보존된다. 이번 회차 요약(`--summary`·`render_results`)은 접두 없는 파일만 센다. 지난 판정을 이번 회차 숫자에 섞지 않는다.
- 판정을 고치고 싶으면 파일을 편집하지 않는다. `verdict.py` 로 새 기록을 더하고 note 에 이유(`감사: …`)를 적는다. 이력이 남아야 나중에 왜 바뀌었는지 설명할 수 있다.

## 8. 확정 기준

다음 중 하나를 만족하면 결함으로 확정한다(`defects.py add`).

- 재확인 레인이 재현함(still)
- 두 레인 이상이 독립적으로 관측함
- 두 회차 연속 같은 F
- 메인이 코드로 원인을 확인함(원인이 증상을 설명함)
- 메인이 증거를 직접 대조함 — 스크린샷을 열어 보고, DB·API 를 읽어 레인이 적은 실제 결과가 맞는지 확인함(값·상태가 남는 결함은 이것만으로 충분하다)

**Critical·Major 후보는 그 회차 안에서 확정한다.** 다음 회차로 미루면 그 회차 보고가 NO-GO 의 진짜 원인을 빠뜨린다. 후보마다 위 방법 중 가장 빠른 것(대개 증거 직접 대조나 코드 판독)으로 확정하고, 안 되면 같은 회차의 재확인 레인에 넣는다. 확정하지 못한 Critical·Major F 는 결함 목록에 없어도 GO 를 막는다(`render_results.py` 가 "감사 전 F"로 센다).

확정하지 못한 Minor·부수 기록은 버리지 않는다. 다음 회차 재확인 목록으로 넘긴다.
