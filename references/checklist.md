## 1. 근거 문서부터 모은다

기대 결과의 출처가 될 수 있는 것만 모은다. 우선순위가 높은 것부터 나열한다.

1. 사람이 확정한 결정 로그(뒤집힌 결정이 표시돼 있는 것)
2. 화면 정의서·시안(Figma 등). 시안은 계속 바뀌므로 읽은 날짜와 장수를 적는다
3. API·DB 설계서(경로·상태코드·오류 code 정본)
4. 이슈별 개발 가이드·공통 계약(화면 문구·상태·오류코드의 실측 부록이 있으면 가장 정확하다)
5. 도메인 요약 위키(파생 층이라 소스와 어긋나면 소스가 이긴다)

**코드는 근거가 아니다.** 코드는 조작 절차(버튼 문구·진입 경로·라우트)를 쓰려고 읽는다. 코드가 하는 일을 기대문으로 베끼면, 코드에 있는 결함이 기대문이 되어 전부 P 로 통과한다. 코드와 명세가 다르면 그 차이를 `notes` 에 결함 후보로 적는다.

## 2. 작성 레인 구성 (`assets/workflows/author.js`)

- 영역 몇 개씩 묶어 **묶음당 레인 하나**로 나눈다. 묶음은 근거 문서가 겹치는 영역끼리 만든다(예: 주문서 작성 + 결제 결과).
- 각 묶음에 넘기는 것은 이름, 영역 문자, 근거 문서 경로(`docs`), 화면 코드 경로(`code`), 메모(`hint`)다.
- 레인은 `RUN/tc-brief.md`(템플릿 `assets/templates/tc-brief.md`)를 먼저 읽는다. 측정 환경·스키마·등급·하지 말 것이 거기 있다. 이 파일에 프로젝트 사실(환경·계정·미구현 목록)을 정확히 채우는 것이 작성 품질을 좌우한다.
- 초안 뒤에 **비평 레인**이 같은 묶음을 다시 본다. 빠진 사용자 행동, 관찰 불가능한 기대문, 내부 이름으로 쓴 절차, 등급 어긋남, 비밀처럼 보이는 값을 찾아 그 파일을 직접 고친다.
- 강한 모델로 돌린다. 작성은 이후 모든 회차의 기준이다.

## 3. TC 스키마와 작성 규칙

| 필드 | 필수 | 규칙 |
|---|:-:|---|
| `id` | ● | 영역 문자 + 두 자리(`D-01`). 영역 문자는 프로필 `areas` 에 있어야 한다 |
| `area` | ● | id 의 영역 문자와 같다 |
| `grade` | ● | 1·2·3(§4) |
| `title` | ● | 사용자가 하는 일 한 줄("회원이 주문서를 끝까지 작성해 제출한다") |
| `steps` | ● | 화면에 보이는 버튼 문구(「」)로 쓴 절차. 문자열("1) … 2) …") 또는 배열 |
| `expected` | ● | 관찰 가능한 결과만 쓴다(화면 문구·이동한 화면·상태코드·응답 필드·DB 값). 문자열 또는 배열 |
| `method` | ● | `ui`·`api`·`ui+api`·`ui+db`·`api+db`·`manual` (프로필 `methods`) |
| `feasibility` | ● | `ok`·`data`·`blocked`(§5) |
| `source` | ● | 근거 문서 경로 + 절. 여러 개면 ` · ` 로 잇는다 |
| `pre` | | 전제(계정 별칭·데이터 상태) |
| `screens` · `route` | | 시안 번호 · 앱 경로(레인이 길을 찾는 데 쓴다) |
| `data_setup` | data 면 ● | 필요한 데이터와 만드는 방법 |
| `feasibility_note` | blocked 면 ● | 왜 이 환경에서 못 재나 |
| `impl` | | `구현`·`부분`·`미구현`(확정된 것만) |
| `notes` | | 근거 미확인 · 코드/명세 차이(결함 후보) · 측정 요령 |

작성 원칙:
- **사용자가 하는 일 하나에 TC 하나.** 화면 하나에 TC 하나가 아니다. 정상 경로 TC 와 중요한 예외 TC(필수값·길이·중복·권한·네트워크 실패·뒤로가기·이중 탭)를 함께 쓴다.
- **끝까지 가는 TC**: 핵심 여정은 마지막 단계(제출·저장·목록 반영)까지 한 TC 로 간다. 중간 단계 TC 만 있으면 "이어 쓰기는 되는데 제출이 안 된다" 같은 결함을 놓친다.
- **관찰 가능한 기대문**: "정상 동작"·"적절히 표시"·"잘 된다"는 쓰지 않는다. `tc_merge.py` 가 「정상 동작」을 거부한다. 문구는 원문 그대로 「」에 넣는다.
- **기대문 하나에 관찰 하나**: 배열로 쪼개면 레인이 일부만 보고 P 를 주는 일이 줄어든다(P = 전부 관찰).
- **비밀 값 금지**: 계정은 별칭으로 쓴다. 실제 번호·인증번호·토큰을 쓰면 `tc_merge.py` 가 거부한다.

## 4. 등급

| 등급 | 기준 | 회차마다 |
|---|---|---|
| 1 | 출시 필수: 핵심 여정(가입·로그인·주문/접수 제출·내역·상세·취소·일정 등 프로젝트의 돈·약속이 걸린 흐름), 보안(인증·인가·타인 정보), 데이터 정합(저장값·금액·상태) | **전부 다시 잰다** |
| 2 | 주요 기능, 주요 예외 처리 | 지난 F·BLOCKED·결함 관련만 |
| 3 | 보조 상태(빈 상태·로딩·오류 문구), 디자인 세부 | 〃 |

등급1 이 전체의 30~50% 를 넘으면 재측정이 1차와 다를 바 없어진다. 등급1 은 "이게 틀리면 출시를 미룬다"에 답할 수 있는 것만 둔다.

## 5. feasibility 와 데이터 준비

- `ok`: 지금 환경에서 앱·API 로 바로 잴 수 있다.
- `data`: 특정 데이터 상태가 필요하다. `data_setup` 에 만드는 법을 쓴다. 앱으로 만들 수 없는 상태(배정·완료 등)는 **UAT 가 만든 행의 어떤 테이블·컬럼을 어떤 값으로** 바꾸면 되는지 서버 코드에서 찾아 적는다. 작성 레인은 실제로 바꾸지 않는다. 이 기록을 모은 것이 상태 시드 도구의 명세가 된다.
- `blocked`: 이 환경으로는 불가능하다(소셜 로그인 실계정·푸시·실기기·iOS·실결제). `feasibility_note` 에 사유를 쓴다. **TC 는 만든다.** 환경이 생기면 그대로 잴 수 있고, 보고서의 "못 잰 것" 목록이 된다.

## 6. 디자인 일관성 TC

같은 역할 화면끼리 같아야 할 것을 TC 로 만든다. 결함의 상당수가 "한 화면만 다르다"였다.
- 헤더: 제목 표시·대비·뒤로가기 위치와 동작
- 주 버튼(CTA): 위치·문구 규칙·비활성 조건
- 진행 표시(단계형 화면): 표기 형식(1/6 등)·단계 수 일치
- 빈 상태·오류 상태: 안내 문구 구조·다시 시도 버튼
- 완료 화면: 이동 버튼·하단 탭 재탭 시 동작

근거는 디자인 시스템·공통 규칙 문서다. 근거가 없는 "더 나은 안"은 결함이 아니라 개선 제안이다. `notes` 에 제안으로 남긴다.

## 7. 종단 저니

영역 TC 는 기능을 하나씩 잰다. 종단 저니는 처음부터 끝까지 이어지는 사용 흐름이다. 예: 신규 가입 → 주문 → 결제 → 내역 확인 → 취소 → 재로그인. 저니 영역(예: Z)에 3~10개를 둔다.
- 단계 사이의 상태 이음매(앞 단계의 선택이 다음 단계에 남는가, 탭을 오가도 유지되는가)에서 결함이 난다.
- 앱 재시작·백그라운드 복귀·네트워크 끊김을 저니 중간에 끼운다.
- 저니는 등급1 로 둔다.

## 8. 병합·검사·렌더

```bash
python $S/tc_merge.py --check     # 쓰지 않고 검사만
python $S/tc_merge.py             # tc-draft/*.jsonl → tc.jsonl
python $S/render_checklist.py --head RUN/checklist-head.md --out <repo>/docs/UAT_체크리스트.md
```

`tc_merge.py` 가 거부하는 것: 필수 필드 누락, id 중복, id 접두와 area 불일치, 프로필에 없는 영역·method, 등급 범위 밖, feasibility 값 오류(data 인데 data_setup 없음 · blocked 인데 사유 없음), 「정상 동작」, 비밀처럼 보이는 값. 문제 목록이 나오면 초안 파일을 고치고 다시 돌린다.

체크리스트 문서는 사람(기획·QA·고객사)이 읽는다. 머리말(`assets/templates/checklist-head.md`)에 목적·합격 기준·환경·판정·심각도·등급·저니를 쉬운 말로 쓴다.

## 9. 2차부터의 정정

- 기대문이 틀렸다고 확인되면 `tc.jsonl` 의 그 줄을 고치고 `notes` 에 `정정 <날짜>: <옛 기대> → <새 기대> (근거)` 를 남긴다. `changes.md` §4 에도 적는다. 확인 근거는 사람 결정이나 명세 갱신이다.
- 사람 결정이 필요한데 아직 없으면 TC 를 고치지 않는다. `changes.md` §2(승인 대기)에 올리고, 레인은 지금 동작을 P + note 「승인 대기」로 기록한다.
- TC 를 지우지 않는다. 범위 밖이 확정되면 NA 로 남는다. id 를 재사용하지 않는다.
- 새 기능·새 결함 경로가 생기면 TC 를 추가한다(이어지는 번호). 추가 사실을 `changes.md` 에 적는다.
- 시안이 바뀌었으면(장수가 늘었으면) 재측정 직전에 다시 읽고, 바뀐 화면의 TC 를 정정한다.

## 10. 흔한 함정

- 코드에서 기대문을 베낌 → 결함이 P 로 통과한다
- 중간에서 끝나는 핵심 여정 TC → 제출 단계 결함을 놓친다
- "보인다"를 트리 존재로 판정하게 쓴 기대문 → 대비·잘림 결함을 놓친다. 시각 기대에는 "스크린샷으로 확인"을 notes 에 적는다
- 한 TC 에 관찰 10개 → 레인이 일부만 보고 P 를 준다. 쪼갠다
- 실제 번호·이름을 예시로 씀 → 문서가 유출 경로가 된다
- 미구현을 TC 에서 뺌 → 보고서에서 "안 쟀다"와 "없다"가 구별되지 않는다. TC 는 두고 `impl` 을 적는다
