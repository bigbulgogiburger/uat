# 결함 — 확정 · 원인 판독 · 트래커 등록 · 수정 루프 · 위반 주입 회귀 테스트

UAT 의 목적은 결함 목록이 아니라 **고쳐진 제품**이다. 이 문서는 확정한 결함을 "다시 나면 빨개지는 테스트"가 붙은 수정으로 바꾸는 과정이다.

## 목차
1. 확정과 중복 방지
2. 원인 판독
3. 트래커 등록
4. 수정 — 위반 주입으로 증명한 회귀 테스트
5. 리뷰
6. 게이트 · 커밋 · 브랜치 쌓기 · 머지
7. 다른 저장소(서버)를 고쳐야 할 때
8. 결함 상태 전이

## 1. 확정과 중복 방지

- 확정 기준은 [judgment.md](judgment.md) §8 이다. 확정한 것만 `defects.py add` 로 `defects.json` 에 올린다.
- ID 는 `UAT<회차>-<두 자리>`(`defects.py next-id --round N`)다. 회차가 바뀌어도 ID 는 그대로다.
- **같은 원인은 한 결함**: 증상이 여러 TC 에 나와도 원인이 하나면 결함 하나에 `tcs` 를 여러 개 단다. 반대로 증상이 같아도 원인이 다르면 나눈다(원인 판독 뒤에 가른다).
- **재발**: 지난 결함이 고쳐졌다가 다시 나면 원래 결함을 `reopened` 로 바꾸고 새 ID 를 만든다. 둘을 `reopened_as` 로 잇는다. 새 결함에는 "이전 수정이 어느 갈래를 놓쳤나"를 적는다. 같은 ID 를 다시 `open` 으로 돌리면 이력이 사라진다.
- 등록 전에 트래커를 검색해 같은 결함이 이미 있는지 본다(제목 키워드·TC ID).

## 2. 원인 판독 — 등록 전에 메인이 한다

증상만 적어 넘기면 수정하는 쪽이 원인을 다시 찾아야 하고, 엉뚱한 곳을 고치기 쉽다. 이 루프가 빨리 수렴한 이유 중 하나가 "원인까지 읽고 등록"이었다.

1. **진짜 오류 문자열부터** 확보한다. 서버 로그의 예외, API 응답 바디의 오류 code, 앱 로그, 콘솔이 그것이다. 없으면 진단 빌드를 쓴다([drivers.md](drivers.md) §4).
2. **진입 지점부터 따라간다.** 화면의 버튼 → 핸들러 → 상태 변경 → 요청 → 서버 검증 순서다. 파일:줄을 적는다.
3. **같은 축의 멀쩡한 경로와 비교한다.** 예: "새로 쓰기는 주소를 남기는데 이어 쓰기만 지운다". 이 비교가 원인을 가장 강하게 확인한다.
4. **설명력 확인**: 원인이 모든 관측(재현 조건·간헐성·우회 방법)을 설명하는가. 간헐 결함이면 타이밍 경합(await 사이에 화면이 다시 그려짐 등)을 의심한다.
5. 확인하지 못했으면 "추정"이라고 쓴다. 수정 방향의 첫 줄에 진단 절차를 둔다. 추정을 사실처럼 쓰면 수정이 엉뚱한 곳을 고치고, 다음 회차에서 재발로 돌아온다.

## 3. 트래커 등록

- **구조**: 회차마다 부모 하나("[UAT N차] 결함 수정 — Critical·Major 0 까지")를 만든다. 그 아래에 원인 단위 하위 이슈를 둔다. 같은 원인이거나 같은 파일을 고치는 결함은 한 하위로 묶는다.
- **본문**: `assets/templates/defect-issue.md` 를 쓴다(현상 · 원인 · 수정 방향 · 영향 TC · 범위 밖). 화면 문구는 「」로 원문 그대로 넣는다. 계정은 별칭으로, 데이터는 UAT 가 만든 번호만 쓴다. 비밀 값·실명·실제 연락처는 쓰지 않는다.
- **우선순위**: Critical = 최상, Major = 상, Minor = 보통. 부모는 하위 중 가장 높은 것을 따른다.
- **연결**: 이전 회차 결함의 재발이면 이전 이슈와 링크한다. 같은 영역을 고친 이전 이슈도 "기반"으로 적는다.
- 등록 뒤 `defects.py set <ID> --tracker <KEY>` 로 잇는다.
- 트래커 MCP 가 없으면 본문을 파일(`RUN/work/issues/<ID>.md`)로 남기고 사람에게 등록을 요청한다.

## 4. 수정 — 위반 주입으로 증명한 회귀 테스트

모든 수정에 **그 결함이 다시 나면 단언으로 빨개지는** 테스트를 붙인다.

### 4.1 실물 흐름으로 세운다

결함이 실제로 나는 조건을 그대로 세운다. 실제 화면 위젯, 실제 라우터, 실제 상태 저장소를 쓰고, 스텁은 결함 경로 밖에만 둔다. 화면을 스텁으로 바꾼 테스트는 화면 사이 이음매에서 나는 결함을 재현하지 못한다. 어떤 결함은 단위 테스트 수천 건이 초록인 채로 살아 있었다.

### 4.2 위반 주입

수정을 되돌리는 주입(예: 고친 줄을 옛 줄로 바꾸는 sed)을 하고, 테스트가 **단언으로** 실패하는지 본다.

```bash
cp <파일> <파일>.bak && sed -i 's/<고친 토큰>/<옛 토큰>/' <파일>
<테스트 명령> > out.txt 2>&1 ; mv <파일>.bak <파일>          # 원복을 판정보다 먼저
# 판정: 출력에서 (1) 컴파일·로드 실패면 BROKEN — 증명 아님
#       (2) 그 테스트 이름(태그)에 붙은 실패 블록(TestFailure/Expected: · JUnit <failure>)이 있으면 FIRED
#       (3) 아니면 SILENT — 테스트가 결함을 못 잡는다
```

- **종료 코드로 판정하지 않는다.** 종료 코드 1 은 컴파일 실패로도 나온다. 반대로 실패 블록 없이 0 이 나오는 러너도 있다. 출력의 실패 블록과 테스트 이름(태그)으로 판정한다.
- **고친 토큰은 파일에 정확히 한 번** 나오게 쓴다. 주석에 같은 토큰을 쓰면 sed 가 주석까지 바꾸거나, 토큰 개수 확인이 틀린다. 주입 전에 토큰 개수를 센다(0 이나 2 이상이면 TOKEN_MISSING 으로 멈춘다).
- 파일 원복을 판정 전에 한다. 판정 스크립트가 중간에 죽어도 작업 트리가 주입된 상태로 남지 않게 한다.
- 테스트 이름에 결함 태그(`<이슈키> r1`)를 넣어 출력에서 찾을 수 있게 한다.

### 4.3 타이밍 결함

"await 사이에 화면이 다시 그려져 위젯이 사라진다" 같은 결함은 비동기 완료 시점을 테스트가 쥐어야 재현된다. 예: 저장소 목의 `clear()` 가 테스트가 가진 Completer 를 기다리게 한다. 그 사이에 프레임을 돌려 재빌드를 일으킨 뒤 Completer 를 완료한다. 고정 지연(sleep·delayed)은 테스트 프레임워크가 타이머를 프레임보다 먼저 소진해 재현이 안 되는 경우가 있다.

### 4.4 범위

- 결함 원인만 고친다. 옆 코드를 "개선"하지 않는다. 디자인 개선은 명세와 일관성을 지키는 범위에서만 하고, 개선이라고 따로 적는다.
- 고친 동작은 다음 회차 `changes.md` §1 에 "화면에서 무엇이 달라졌나"로 적는다.
- 사람 결정이 필요한 갈래(기대문 충돌·정책)는 고치지 않고 "범위 밖 · 승인 대기"로 남긴다.

## 5. 리뷰

- 외부 리뷰어(다른 모델·도구)를 쓰면 **판정이 실제로 나왔는지 출력 본문을 확인한다.** 종료 코드 0 인데 프롬프트만 되풀이하고 판정 없이 끝난 경우가 있었다. 출력 끝의 판정 줄(Verdict 등)을 찾는다.
- "사용량 한도" 메시지는 출력 전체를 grep 하면 오탐이 난다. 본문 중의 숫자(429 등)에 걸린다. 끝부분과 판정 줄을 본다.
- 리뷰 지적은 메인이 코드로 확인한 뒤 확정하거나 기각한다. 기각 이유를 남긴다.

## 6. 게이트 · 커밋 · 브랜치 쌓기 · 머지

- 하위 이슈 묶음마다 브랜치 하나를 쓰고, **직전 묶음 브랜치 위에 쌓는다.** 다음 회차는 스택 끝 커밋 하나로 빌드한다. 머지는 사람이 한다. 쌓인 순서대로 머지해야 한다는 것을 보고에 적는다.
- 프로젝트에 이슈 하네스(게이트·리뷰·커밋 훅)가 있으면 그것을 쓴다. 훅이 막으면 사유대로 고친다. 훅 우회(`--no-verify`·훅 끄기)는 하지 않는다.
- 전량 테스트·빌드·게이트는 **측정이 끝난 뒤에** 한 번 돌린다. 측정 기기·서버와 메모리를 다툰다.
- 커밋 메시지에 "왜"를 남긴다(어느 UAT 결함·어느 TC). 비밀 값은 쓰지 않는다.

## 7. 다른 저장소(서버)를 고쳐야 할 때

- 먼저 측정 대상 저장소 안에서 고칠 수 있는지 본다(호출 방식·검증·폴백). 다른 팀 서버를 고치는 비용은 크다.
- 정말 필요하면 그 저장소에 **별도 브랜치**를 판다. 원본 브랜치에 직접 커밋하지 않는다. 그 저장소의 규칙(커밋·리뷰)을 따른다.
- 다른 저장소의 변경은 머지 순서와 배포 게이트에 영향을 준다. 보고서의 "사람 승인 대기"에 올린다.

## 8. 결함 상태 전이

```
open ──(수정 반영·QA 전이)──> qa ──(재측정에서 관련 TC 전부 P · 재확인 fixed)──> fixed
  │                            └──(재측정에서 재발)──> reopened ──> 새 ID(open) 로 이어짐
  ├──(사람이 보류 수용)──> accepted        GO 판정에서 미해결로 세지 않음 · 보고서에 명시
  └──(다른 결함과 같은 원인)──> dup
```

- `fixed` 는 재측정 증거가 있을 때만 단다. 코드가 머지됐다는 것은 fixed 의 근거가 아니다.
- `accepted` 는 사람 결정이 있어야 한다. 누가 언제 결정했는지 `--note` 로 남긴다.
