# 레인 — 분할 · 프롬프트 · Workflow 운용 · 감시 · 재개

레인은 TC 묶음 하나를 맡아 실제로 재는 에이전트 한 명이다. 이 루프의 결과 품질은 대부분 레인 설계에서 나온다. 무엇을 한 레인에 묶나, 무엇을 읽히나, 무엇을 돌려받나가 핵심이다.

## 1. 왜 레인으로 나누나

- **맥락 한계**: 한 에이전트가 100개 넘는 TC 를 재면 앞에서 읽은 규칙(외부 발송 금지·증거 필수)을 뒤에서 잊는다. TC 16개 안팎이 규칙을 끝까지 지키는 크기였다.
- **자원 배타**: 기기·계정·브라우저 세션은 공유하면 서로의 상태를 깨뜨린다. 레인이 자원을 배타적으로 가지면 "누가 로그아웃시켰나" 같은 유령 결함이 사라진다.
- **병렬**: API 레인은 기기를 쓰지 않으므로 UI 레인과 동시에 돈다. 회차 시간이 대략 UI 레인 합계로 줄어든다.
- **책임 추적**: 판정 jsonl 이 레인별 파일이라, 이상한 판정이 나오면 그 레인의 메모·프롬프트만 고치면 된다.

## 2. 분할 규칙 (`plan_lanes.py` 가 프로필 `lanes.*` 로 한다)

| 규칙 | 이유 |
|---|---|
| `method` 가 `api_methods` 면 API 레인(`api_chunk` 개씩) | 기기 불필요 → UI 와 병렬 |
| API 레인끼리는 **직렬** | 같은 전용 계정 토큰을 동시에 돌리면 토큰 회전·재사용 감지가 서로의 세션을 끊는다 |
| `ui_groups` 순서대로, 기기당 동시에 `ui_parallel` 개 | 기기 하나를 두 레인이 쓰면 화면이 엉킨다. 웹은 브라우저 컨텍스트를 나눌 수 있으면 올린다 |
| `route_rules` 로 성격이 같은 TC 를 한 레인에 모은다 | 예: 「탈퇴·로그아웃」 TC 는 영역과 상관없이 auth 레인으로. 세션 파괴가 한 곳에서만 일어난다 |
| `after_api` 레인은 API 레인이 끝난 뒤에 | 세션·계정을 파괴하는 레인이 API 레인의 전제를 깨지 않게 |
| `isolated` TC 는 별도 레인으로 맨 끝 | 서버를 내렸다 올리는 TC 가 다른 레인의 측정 중에 일어나면 그 레인 판정이 오염된다 |
| `chunk`(기본 16) 넘으면 균등 분할 | §1 맥락 한계 |
| 어디에도 안 걸린 TC 는 `misc` 레인 + 경고 | 프로필의 영역 매핑이 빠졌다는 신호다. 프로필을 고친다 |

2차부터 `remeasure` 는 등급1 ∪ 지난 F·BLOCKED ∪ 미해결 결함의 TC ∪ 미측정 ∪ `--extra` 를 고른다. 이유는 `lanes/why.json` 에 TC 별로 남는다. 보고서에서 "왜 이 TC 를 다시 쟀나"에 답할 때 쓴다. `--skip` 은 결함·extra 로 고른 TC 는 빼지 않는다.

## 3. 레인 프롬프트의 구성 (`assets/workflows/measure.js`)

레인은 아래 순서로 읽는다. 순서 자체가 우선순위다.

1. **레인 가이드**: 절대 규칙·도구·판정·심각도. 회차 간 공유한다.
2. **`lanes/changes.md`** (2차부터): 지난 회차 이후 의도해서 바뀐 동작·승인 대기·수용된 보류. 가이드와 다르면 이것이 이긴다. 이게 없으면 레인이 고친 동작을 "예전과 다르다"며 결함으로 잡는다.
3. **`lanes/notes-<lane>.md`**: 그 레인이 지난 회차에 쌓은 절차·우회. 같은 시행착오를 반복하지 않게 한다.
4. **배정 TC 파일**: 원문 JSONL 이다. `source` 를 열어 기대문을 확인할 수 있다.
5. **지난 판정** `out/r<N>-<lane>.jsonl`: 지난 F 의 재현 절차를 그대로 밟기 위해 읽는다.

프롬프트에 직접 넣는 것은 레인 이름, 배정 TC ID 목록, 빌드 sha, 경로뿐이다. 규칙 본문은 파일로 읽힌다. 프롬프트에 규칙을 복사하면 회차마다 어긋나는 사본이 생긴다.

반환은 구조화 출력(schema)이다: `counts · f_list · blocked · side · fixed_confirmed · created_data · unjudged · end_state · notes`. 메인은 이 반환으로 다음 레인 시작 상태를 확인하고(`end_state`), 감사 대상을 고른다. **판정 수는 반환이 아니라 jsonl 에서 센다.** 반환은 요약이고 jsonl 이 원본이다.

## 4. 모델과 추론 강도

- 측정 레인은 **가장 강한 모델 · 높은 추론 강도**(`lanes.model`·`lanes.effort`, 기본 opus · xhigh)로 돈다. 측정 레인은 화면을 읽고, 기대문과 대조하고, 다른 길을 찾고, 오판을 피해야 한다. 판단의 연속이라 약한 모델은 "없다" F 와 근거 없는 P 를 쏟아낸다. 결과가 기대보다 좋았던 가장 큰 이유가 여기 있었다.
- 작성 레인(author)도 강한 모델로 돌린다. 기대문이 틀리면 이후 모든 회차가 틀린다.
- 단순 반복(로그 grep, 파일 정리)만 하는 보조 레인은 가벼운 모델로 충분하다.
- 메인 세션이 최상위 모델이면, 감사·결함 확정·원인 판독은 위임하지 않고 메인이 직접 한다.

## 5. Workflow 운용

```bash
python $S/plan_lanes.py args --out RUN/lanes/workflow-args.json
# Workflow scriptPath=$SKILL/assets/workflows/measure.js  args=<workflow-args.json 의 내용을 JSON 값으로>
```

- `args` 는 JSON **값**으로 넘긴다. 문자열로 직렬화해 넘기면 스크립트가 배열을 못 읽는다.
- Workflow 스크립트는 파일을 읽지 못하고 시계도 쓰지 못한다. 경로와 시각은 args 로 넘기고, 파일은 레인 에이전트가 읽는다.
- Workflow 는 백그라운드로 돈다. 도는 동안 메인은 다음 일을 한다. 지난 회차 결함의 원인 판독, 수정 계획, 보고서 초안 같은 일이다. 단, 빌드·테스트·게이트는 측정이 끝난 뒤에 돌린다(메모리·CPU·기기 경합).
- 완료 알림이 오면 반환을 먼저 본다. 반환이 비었거나 이상하면 transcript 폴더의 `journal.jsonl` 을 읽는다. 각 에이전트의 실제 반환이 거기 있다.

## 6. 감시와 개입

- 측정 중에는 `ui.py dump` 나 스크린샷으로 기기를 들여다보지 않는다. 메인이 기기를 만지면 레인의 화면이 바뀐다.
- 진행은 `out/<lane>.jsonl` 줄 수와 `verdict.py --summary` 로 본다. 파일 시각이 오래 멈췄으면 레인이 막힌 것이다.
- 서버 로그·수신기 로그(`work/sink.log`)는 메인이 봐도 된다. 실제 외부 발송 흔적이 보이면 Workflow 를 멈춘다(TaskStop).
- 여유 메모리를 주기적으로 본다(`memguard.py --min 1.5`). 모자라면 허용된 유휴 프로세스(빌드 데몬 등)만 정리한다. 측정 중인 서버·기기·사용자 프로그램은 건드리지 않는다.

## 7. 죽은 레인 · 재개

- 레인 에이전트가 API 오류로 죽으면 그 레인 반환은 `null` 이다. measure.js 는 그 묶음을 `unjudged` 로 채워 돌려준다. **결과가 없다는 사실을 기록하고**, 그 묶음만 다시 돌린다.
- Workflow 재개(`resumeFromRunId`)의 캐시는 **같은 run 의 같은 (프롬프트, 옵션)** 에만 맞는다. 다른 run 에서 끝난 레인을 재개 인자에 넣으면 그 레인이 처음부터 다시 돈다. 재개 전에 journal 의 label 을 대조하고, 아니면 남은 레인만 담은 args 로 새 run 을 띄운다.
- 레인이 중간에 죽어도 그때까지 쓴 판정은 jsonl 에 남는다. 다시 돌릴 때 이미 판정된 TC 를 빼려면 `plan_lanes.py remeasure` 로 다시 고르거나 args 의 `ids` 를 줄인다.

## 8. 레인 메모 (`lanes/notes-<lane>.md`)

레인이 알게 된 **그 레인만의 요령**을 메인이 회차 끝에 정리해 둔다.
- 화면 진입 경로, 대기 문구, 스크롤 위치
- 데이터 만드는 순서(어느 계정으로 무엇을 먼저)
- 막혔던 곳과 우회(우회가 결함 덕분이면 결함 ID 를 함께 적는다. 고쳐지면 지운다)

레인 메모는 결함 기록이 아니다. 결함은 verdict.py 로만 남긴다. 메모가 길어지면(50줄 이상) 가이드로 올릴 것과 지울 것을 가른다. 프로젝트 공통 드라이버 요령은 `work/driver-notes.md`(템플릿 `assets/templates/driver-notes.md`)에 둔다.

## 9. 대안 실행기

- **Agent 툴 순차 실행**: Workflow 툴이 없는 세션에서는 measure.js 의 `prompt()` 와 같은 내용을 Agent 툴에 넘겨 레인을 하나씩 돌린다. 반환은 JSON 텍스트로 받아 직접 파싱한다.
- **Herdr pane 의 에이전트**: 다른 터미널의 에이전트(다른 모델·다른 CLI)를 레인으로 쓸 수 있다. 장점은 메인 세션 맥락을 쓰지 않는다는 것이다. 단점은 pane 하나에 0.5~0.7GB 메모리가 들고, 반환이 구조화돼 있지 않다는 것이다. 레인에게 "끝나면 결과를 파일로 쓰고 경로만 답하라"고 시킨다. 판정은 어느 실행기든 verdict.py 로만 남기므로 감사 절차는 같다.
- 무엇으로 돌리든 **레인 보고를 믿지 말고 jsonl 로 대조한다.**
