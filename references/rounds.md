## 1. 회차 사이에 하는 일

```
N차 측정 끝 ─ triage · 감사 · 재확인(recheck) ─ 결함 확정 · 분류 · 원인 판독 ─ 트래커 등록
   ─ 수정 루프(브랜치 쌓기 · 위반 주입 테스트 · 리뷰 · 게이트) ─ 스택 끝 커밋 확정
   ─ N차 보고서 절 렌더 ─ init_run --round N+1 --prev N차 ─ 서버·앱을 그 커밋으로 빌드·배포
   ─ changes.md · recheck.md ─ plan_lanes remeasure · args ─ N+1차 측정
```

- 수정이 전부 끝나기 전에 다음 회차를 시작하지 않는다. 일부만 고친 빌드로 재면 나머지 결함이 다시 F 로 나와 감사 비용만 든다. 예외는 한 결함이 진단을 위해 실기 측정을 기다리는 경우다. 그때는 그 결함만 다음 회차로 넘기고, 넘긴 사실을 changes.md 에 적는다.
- 빌드 전에 스택 끝 커밋에 모든 수정이 들어 있는지 확인한다(`git log --oneline <base>..<tip>`).
- 측정 DB 스키마가 새 커밋 기대치인지 다시 확인한다. 수정에 마이그레이션이 들어 있으면 먼저 적용한다(사람 승인이 필요한 환경이면 승인 대기로 둔다).

## 2. changes.md 쓰기 (`assets/templates/changes.md`)

레인이 기준으로 삼는 문서다. 가이드와 다르면 이것이 이긴다.

- **§1 의도해서 바뀐 동작**: 이슈 하나에 한 단락이다. "화면에서 무엇이 보이는가"로 쓰고 코드 이름은 쓰지 않는다. 영향 TC 를 단다. 레인은 이 문단을 보고 "예전과 다르다"를 결함으로 잡지 않는다.
- **§2 사람 승인 대기**: 지금 동작을 P + note 로 기록하게 한다. 회차 중에 사람에게 하나씩 묻지 않는다. 모아서 회차 끝에 묻는다.
- **§3 수용된 보류**: F 로 기록하되 GO 판정에서 미해결로 세지 않는다. 근거(누가·언제)를 적는다.
- **§4 기대문 정정**: tc.jsonl 에 반영한 정정이다.
- **§5 측정 환경 변화**: 계정·도구·포트 같은 변화다.
- **§6 지난 회차들**: 누적한다. 지우면 레인이 2회차 전에 바뀐 동작을 다시 결함으로 잡는다.

## 3. recheck.md 쓰기 (`assets/templates/recheck.md`)

- 확정하지 못한 부수 결함, 고쳤다고 한 부수 결함(TC 밖이라 재측정 레인이 안 밟는 것)을 적는다. 각 항목에 시작 상태·재현 절차·예전 현상·고쳐진 동작·갈래·정리를 쓴다.
- "순서 필요" BLOCKED TC 묶음과 그 상태를 만드는 법도 여기 적는다(`recheck.js` 의 ordered).
- 재확인은 측정 레인이 끝난 뒤 같은 기기로 돈다.

## 4. 재측정 범위

`plan_lanes.py remeasure` 의 기본 선택은 다음의 합집합이다.
- **등급1 전부**: 고친 코드가 다른 핵심 여정을 깨뜨리지 않았는지 본다(회귀).
- **지난 F·BLOCKED**: 고쳐졌는지, 환경이 생겼는지 본다.
- **미해결 결함의 TC**(open·qa·reopened)
- **미측정**: 지난 회차에 기록이 없던 TC(레인 사망 등)
- **`--extra`**: 수정이 닿은 화면의 등급2·3 TC 처럼 메인이 고른 것

`lanes/why.json` 에 TC 별 선택 이유가 남는다. 회차가 거듭되면 선택 수가 줄어 회차 시간이 짧아진다. 등급1 비중이 크면 줄지 않으므로 등급을 다시 본다([checklist.md](checklist.md) §4).

## 5. 보고서

```bash
python $S/render_results.py --stats                       # 숫자만(JSON) — 손으로 세지 않는다
python $S/render_results.py --round N --date <날짜> --build <sha> --out <repo>/docs/UAT_결과보고.md --note "…"
```

- 회차마다 절 하나다. 같은 회차 절은 덮어쓰고, 다른 회차 절은 보존한다. 그래서 문서 하나에 1차부터 지금까지의 경과가 남는다.
- 스크립트가 쓰는 것: 빌드 · GO/NO-GO 와 미해결 Critical·Major·Minor · TC 현재 상태 분포 · 확정 결함 표(감사 전이면 F 목록) · 영역별 상태 · 등급1 미통과 · BLOCKED 사유 · TC 밖 결함 · 결함 상세(현상·원인·재현·증거) · TC 별 전체 판정(접힘).
- `--note` 로 더하는 것(한 줄씩, 여러 번): 이번 회차 범위("117 TC — 등급1 ∪ 지난 F·BLOCKED · 선택 이유는 why.json"), 사람 승인 대기 요약, 수용된 보류와 GO 판정에서 어떻게 셌는지, 다음 회차 계획.
- 보고서의 비밀 규칙은 판정과 같다. 별칭만 쓰고, 번호·토큰·실명은 쓰지 않는다.
- 판정 문서(jsonl)가 원본이다. 보고서를 손으로 고쳤다면 다음 렌더에서 덮인다. 고칠 것은 jsonl(verdict.py)이나 defects.json(defects.py)에서 고친다.

## 6. 사용자에게 알리기

- 회차가 끝날 때마다 짧게 보고한다. 결함 ID 나 규칙 번호가 아니라 **화면에서 무엇이 잘못 보이나**를 쉬운 말로 먼저 쓴다. 예: "이어 쓴 주문서가 마지막에 제출되지 않아요(Critical)", "탈퇴는 되는데 완료 화면이 안 떠요(Major)".
- 숫자는 `--stats` 에서 가져온다: 잰 TC 수, P/F/BLOCKED, 미해결 Critical·Major 수, GO/NO-GO.
- 사람 결정이 필요한 항목은 회차 끝에 한 번에 묶어서 묻는다. 각 항목에 "지금 동작 / 대안 / 권장"을 붙인다.
- 장시간 무인으로 돌 때는 회차 사이에 진행 한두 줄을 남긴다. 사용자가 다른 기기에서 진행을 볼 수 있다.

## 7. 종료와 정리

**끝**: 미해결 확정 결함 Critical 0 · Major 0 이고 등급1 전부가 P · NA · 수용된 보류다. Minor 는 목록으로 남긴다.

**멈추고 보고**:
1. 같은 결함이 2회차 연속 해소되지 않음 → 접근을 바꿔야 한다(진단 부족·설계 문제)
2. 여유 메모리 < 1.5GB 가 계속됨 → 레인을 띄울 수 없다
3. 같은 게이트가 2회 연속 실패
4. 실제 외부 발송 흔적
5. 사람만 정할 수 있는 결정이 결함 판정을 막음

**정리** (끝나거나 멈출 때):
- 상태 시드 도구로 손댄 행을 `revert` 한다. `db.py revert --dry` 로 원복 목록을 먼저 보고, 원복한다.
- 원복 순서에 주의한다. 자식 행(첨부·이력)을 먼저 지우고 부모 상태를 되돌린다. 사람이 보존하기로 한 데이터(예: 평가 기록)는 원복 대상에서 뺀다.
- 기기 설정(키보드 앱·글자 크기·회전·네트워크)을 되돌린다.
- 만든 데이터 목록(`work/requests.jsonl`)과 남긴 데이터(원복하지 않은 것과 이유)를 보고서에 적는다.
- 더 쓰지 않는 수신기·서버·에뮬레이터 pane 을 닫는다. 사용자가 띄운 것은 닫지 않는다.
