# <프로젝트> UAT 1차 — 테스트 항목(TC) 작성 규칙

> 템플릿이다. `<…>` 를 채워 `RUN/tc-brief.md` 로 둔다. 작성 레인(author 워크플로)이 이 파일을 먼저 끝까지 읽는다.

당신은 <프로젝트 한 줄 설명>의 **인수 테스트(UAT) 항목 초안**을 쓴다. 다른 사람(에이전트)이 이 항목을 보고
<기기/브라우저>에서 앱을 직접 조작하거나 API 를 직접 호출해 P/F 를 판정한다.
틀린 기대문으로 재면 틀린 F 가 나온다. **기대 결과는 반드시 명세 근거에서 가져오고, 근거가 없으면 지어내지 않는다.**

## 측정 환경 (고정)

- 저장소 `<경로>` <브랜치>(HEAD `<sha>`) — <구성: 서버/클라이언트>
- 서버 `<base_url>` (기기에서는 `<에뮬레이터용 주소>`) · DB = <공유/전용 · 스키마>
- 함께 띄우는 서버: <목록> · 띄우지 않는 서버: <목록과 이유>
- 기기 <모델 · 해상도 · OS> · 앱은 <debug/release> 빌드
- 로그인: <테스트 계정 수와 성격>. 번호·인증번호·비밀번호 값은 TC 에 쓰지 않는다. `계정#1`·`계정#2` 로만 부른다.
- 이 환경에서 못 하는 것: <소셜 로그인 실계정 · 푸시 · 실기기 · iOS · 실결제> → TC 는 만들되 `feasibility` 에 사유를 적는다.
- 미구현으로 확정된 것: <기능 · 근거> → TC 는 만들되 `impl: "미구현"`.

## 읽을 것 (당신의 영역 묶음에 해당하는 것만)

1. <도메인 요약 문서 위치> — 현재 규칙 요약. 소스와 어긋나면 소스가 이긴다.
2. <화면 문구·상태·오류코드의 정본 문서 위치>
3. <기획 정본 · API 정본 · 결정 로그>
4. 화면 코드 `<경로 패턴>` — **조작 절차를 쓰려고** 읽는다(버튼 문구·진입 경로·라우트). 코드가 하는 일을 기대 결과로 베끼지 않는다. 기대 결과는 명세에서 온다. 코드와 명세가 다르면 그 자체가 결함 후보이니 `notes` 에 적는다.
5. 라우트 정의: `<경로>`

## TC 한 줄 = JSON 한 줄 (JSONL)

```json
{"id":"D-01","area":"D","grade":1,"title":"…","screens":["<시안 번호>"],"route":"<앱 경로>",
 "pre":"전제(로그인 계정·데이터 상태)","steps":["…","…"],"expected":["관찰 가능한 결과 1","…"],
 "source":"<근거 문서 경로 §절>","method":"ui|api|ui+api|ui+db|api+db|manual",
 "data_setup":"필요한 데이터와 만드는 방법(없으면 \"\")","feasibility":"ok|data|blocked","feasibility_note":"…",
 "impl":"구현|부분|미구현","notes":"…"}
```

- `id`: 영역 문자 + 두 자리 순번(`D-01`…). 영역 문자는 지시에서 받은 것만 쓴다.
- `grade`: **1** = 출시 필수(핵심 여정 — <나열> — 과 보안·데이터 정합. 실패하면 출시 불가) · **2** = 주요 기능·주요 예외 처리 · **3** = 보조 상태(빈 상태·로딩·오류 문구)·디자인 세부.
- `steps`: 사람이 그대로 따라 할 수 있게 **화면에 보이는 버튼 문구**로 쓴다(「」로 감싼다). API TC 는 메서드·경로·헤더·바디를 쓴다.
- `expected`: 관찰 가능한 것만 쓴다(화면 문구·이동한 화면·API 상태코드·응답 필드·DB 값). "정상 동작"·"적절히" 같은 말은 쓰지 않는다.
- `method`: `ui`(화면) · `api`(직접 호출) · `ui+api` · `ui+db`(화면 조작 뒤 DB 를 **읽어서** 확인) · `manual`(사람만 가능).
- `feasibility`: `ok`(지금 환경에서 잴 수 있음) · `data`(특정 데이터 상태가 필요 — `data_setup` 에 만드는 방법) · `blocked`(이 환경으로는 불가 — 사유 필수).
  - 앱이 만들 수 없는 진행 상태가 필요한 TC 는 `data` 로 두고, **UAT 가 만든 행의 어떤 테이블·컬럼을 어떤 값으로 바꾸면 되는지**를 서버 코드에서 찾아 `data_setup` 에 적는다(실제로 바꾸지는 않는다). 이 기록이 상태 시드 도구의 명세가 된다.
- 화면 하나에 TC 하나가 아니다. **사용자가 하는 일 하나**에 TC 하나다. 정상 경로에 중요한 예외·검증(필수값·길이 제한·중복·권한·네트워크 실패·뒤로가기)을 섞는다.
- 끝까지 가는 TC 를 쓴다. 임시저장 → 이어 쓰기 → **제출**처럼 중간에서 멈추면 마지막 단계에서만 터지는 결함을 놓친다.
- 디자인 일관성 TC 도 넣는다. 그 영역 화면들에서 같아야 할 것(제목 표시·뒤로가기·주 버튼 위치·진행 표시·빈 상태)을 근거(디자인 시스템·공통 규칙)와 함께 쓴다.

## 하지 말 것

- 이 파일과 배정된 초안 파일 말고는 고치지 않는다. 앱·서버를 실행하지 않는다. DB 에 쓰지 않는다.
- 근거 없는 기대 결과를 만들지 않는다. 근거를 못 찾으면 그 TC 의 `notes` 에 "근거 미확인"을 적는다.
- 번호·인증번호·토큰·비밀번호 값을 어디에도 쓰지 않는다.
